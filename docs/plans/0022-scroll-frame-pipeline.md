# 스크롤 프레임 갱신 통합 (#80 후속)

## 문제와 결정

- 느린 전환 중에도 끊김 피드백이 있어 같은 로컬 프로덕션·Chrome 1512×982 환경에서 rAF 간격과 긴 작업을 측정한다.
- 변경 전 warm record→report와 report→record의 프레임 간격 중앙값이 약 33.3ms였다. 첫 3D 로딩에는 약 346ms의 긴 작업도 있었다.
- 기존 화면 갱신·각 보간 hook의 별도 rAF·Spline의 두 즉시 렌더 경로를 공통 시계로 묶는다.
- 공통 루프는 DOM → 같은 반감기의 보간 그룹 → 캔버스 후처리 순서다. 같은 보간 그룹은 위치·시간을 공유하고 3D 즉시 렌더는 마지막에 한 번만 수행한다.
- Spline 런타임은 공식 생성자 옵션 `renderMode: "manual"`로 생성한다. 후처리에서 `requestRender()`로 그리기를 요청하고 기존 즉시 렌더 경로로 같은 프레임의 DOM과 맞춘다. 자동 렌더와 중복되던 그리기를 제거한다.
- viewport 계산·미디어 쿼리 생성은 프레임마다 반복하지 않고 리사이즈와 설정 변경에 대응한다.
- 기존 5초 전환, 완만한 곡선, 번호 제거와 3D 해상도는 유지한다. 문구의 별도 등장 모션은 아래 후속 피드백에 따라 제거했다.

## 검증

- [x] DOM·보간 갱신 뒤 캔버스 한 번 그리기 명세
- [x] 같은 반감기 동기화·정지 후 따라잡기·동작 줄이기·구독 해제 명세
- [x] 같은 구간의 전후 프레임 측정
- [x] 3D·단계 이동·모바일·동작 줄이기 회귀 검증
- [x] 타입·린트·FSD·304개 테스트·프로덕션 빌드

## 측정 주의

로컬 headless Chrome 측정은 물리 맥북 화면의 FPS를 보장하지 않는다. 첫 방문의 런타임·씬 파싱과 이미 준비된 3D의 전환을 구분해 기록한다.

## 전후 측정

로컬 프로덕션·같은 Chrome·1512×982, 각 구간 약 5.6초. 구간 내 모든 rAF 간격을 수집했다. 준비된 구간에는 긴 작업이 없었다.

| 준비된 전환 구간 | 이전 중앙 간격 | 이후 중앙 간격 | 25ms 초과 프레임 전→후 |
| ---------------- | -------------- | -------------- | ---------------------- |
| record → report  | 33.3ms         | 16.7ms         | 132 → 63               |
| report → record  | 33.3ms         | 16.7ms         | 118 → 41               |

루프 통합만으로는 개선되지 않아 수동 렌더 경로까지 함께 적용한 최종 결과다. 간헐적인 33ms 간격은 남으며, 첫 런타임·씬 로딩에는 긴 작업이 남아 있다. 첫 로딩 최대 간격은 샘플마다 200~350ms로 달라져 개선을 주장하지 않는다.

## 기능 회귀

- record·report·recommend·ar·share·closing과 역방향 share 복귀를 실제 Spline 캔버스로 검증했다. 캡처에서 폰·카드·화면 위치를 확인했다.
- 390×844 모바일은 캔버스 없이 자유 스크롤을 유지한다. 동작 줄이기에서는 캔버스를 시작하지 않고 즉시 다음 화면으로 이동한다.
- 브라우저 런타임 오류 0건. 캡처와 결과는 로컬 `.snapshots/frame-pipeline/`.
- 최종 빌드에서 씬 다운로드를 차단해 CSS 폰 대체 표시를 확인했다. 실패한 런타임은 dispose하여 리소스를 정리한다.
- 전후 측정 원본은 `.snapshots/frame-pipeline/frames-before.json`, `frames-after.json`에 저장했다.
