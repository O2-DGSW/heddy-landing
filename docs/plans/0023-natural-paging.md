# 데스크톱 화면 넘김을 배민처럼 자연스럽게 (이슈 #82)

## 왜

휠 한 번으로 화면을 넘길 때 "억지로 끌어당기는" 느낌이 난다(사용자 피드백). 배민(baemin.com)처럼 부드럽고 자연스럽게 이동해야 한다.

## 기준: 배민 측정 (2026-10-17, Chrome 1512×862, 실제 휠 1px × 2회)

| 경과 | 100ms | 210ms  | 310ms  | 410ms  | 510ms  | 610ms  | 710ms | 850~900ms |
| ---- | ----- | ------ | ------ | ------ | ------ | ------ | ----- | --------- |
| 진행 | 6~8%  | 26~30% | 51~54% | 69~72% | 82~84% | 90~92% | 96%   | 99.7%     |

- 입력 후 약 60~120ms 안에 움직이기 시작하고, **한 화면을 약 0.9초**에 이동한다.
- 짧게 부드럽게 출발해 앞쪽에서 빠르게 가고 길게 감속한다 — `cubic-bezier(0.4, 0, 0.2, 1)`에 가깝다.
- 이동하는 것은 늘 **화면 한 장(100vh)**이고, 도착한 뒤 그 화면의 요소가 등장한다.

## 원인 (지금 구현: 한 입력 = 다음 멈춤 지점까지 5초, easeInOutSine 한 곡선)

헤디 섹션은 sticky라서 스크롤 길이 대부분은 "화면은 그대로이고 폰·카드만 움직이는 구간"이고, 실제로 다음 화면이 미끄러져 올라오는 것은 섹션 경계의 **한 화면 구간**뿐이다. 그런데 멈춤 지점 사이 스크롤 거리(1.2~7.8화면)를 전부 같은 5초 곡선 하나로 끌고 가서, 화면이 미끄러지는 순간의 속도가 전환마다 제각각이다.

| 전환          | 이동 거리 | 다음 화면이 올라오는 구간(5초 중)                                |
| ------------- | --------- | ---------------------------------------------------------------- |
| 인트로 → 기록 | 7.8화면   | 1.60~2.04초 (0.45초, 그 전 1.6초는 숨은 구간이라 화면 변화 없음) |
| 기록 → 리포트 | 2.1화면   | 0~2.40초 (2.4초)                                                 |
| 리포트 → 추천 | 2.1화면   | 0.55~2.55초 (2.0초)                                              |
| 추천 → AR     | 6.8화면   | 1.39~1.93초 (0.54초)                                             |
| AR → 공유     | 3.4화면   | 1.11~2.21초 (1.1초)                                              |
| 공유 → 마지막 | 1.2화면   | 1.26~5.00초 (3.7초)                                              |

1. **입력과 화면 반응이 어긋남** — 휠을 굴려도 1.4~1.6초 동안 화면이 그대로다가(숨은 구간·섹션 안 모션을 먼저 지나감) 갑자기 0.45초 만에 다음 화면이 휙 올라온다. 이게 "끌어당기는" 느낌의 핵심이다.
2. **같은 동작의 속도가 매번 다름** — 한 화면 이동이 0.45초일 때도 3.7초일 때도 있다.
3. **5초 동안 입력을 막음** — 도착 후 모션을 보는 중에도 다음으로 갈 수 없어 조작을 빼앗긴 느낌이 든다.

## 설계

한 번의 전환을 스크롤 경로의 성격대로 **구간(segment)**으로 나누고, 구간마다 알맞은 시간·곡선을 준다. 실제 scrollY를 움직이는 방식은 유지해 3D 폰과 섹션 모션은 그대로 재생된다.

| 구간                                                      | 화면에 보이는 것                       | 시간                                  | 곡선                                    |
| --------------------------------------------------------- | -------------------------------------- | ------------------------------------- | --------------------------------------- |
| **숨은 구간** — 인트로 sticky(폰 숨김, 합체)              | 변화 없음                              | 0 (바로 건너뜀)                       | —                                       |
| **떠나기** — 지금 섹션의 남은 모션(멈춤 지점 → sticky 끝) | 지금 화면의 모션 마무리                | 짧게: 화면당 240ms, 최대 700ms        | easeInOutSine                           |
| **화면 이동** — 섹션 경계 한 화면(다음 섹션이 올라옴)     | 화면 전체가 미끄러짐                   | **항상 900ms**                        | **cubic-bezier(0.4, 0, 0.2, 1)** (배민) |
| **도착** — 다음 섹션 sticky 시작 → 멈춤 지점              | 새 화면의 모션(기록 쌓임·카드 펼침·AR) | 화면당 420ms(AR 600ms), [400, 3000]ms | easeInOutSine                           |
| 지나가는 섹션(점 내비로 여러 칸)                          | 중간 섹션 모션                         | 화면당 160ms                          | easeInOutSine                           |

- 구간 나누기는 섹션 이름이 아니라 기하로 한다: 섹션의 sticky 범위 `[top, end − 화면 높이]` 안이면 "화면 고정" 구간, 그 밖은 전부 "화면 이동" 구간이다(섹션 경계·마지막 → 푸터 포함). 화면 이동 구간이 한 화면보다 짧으면(푸터) 시간은 `900ms × √(거리/화면)`, 최소 450ms.
- 화면 이동 구간은 sticky라 화면이 멈춰 있는 떠나기·도착 구간과 맞닿아도 화면 위치가 튀지 않는다(화면 위치는 이동 구간에서만 변한다).
- 같은 섹션 안 멈춤 지점끼리(있다면)는 도착 규칙만 쓴다.
- 결과: 모든 전환에서 **다음 화면은 항상 0.9초 같은 곡선으로** 올라오고, 숨은 구간이 없어져 휠 직후 바로 반응한다. 기록 쌓임처럼 긴 모션은 도착 뒤 2.2초 안에 감속하며 완성된다.

### 입력

- **화면 이동 중**에는 새 입력을 받지 않는다(배민과 같음, 관성 꼬리는 한 제스처로 소비하는 기존 규칙 유지).
- **떠나기·도착 중** 새 제스처는 바로 받는다: 같은 방향이면 지금 위치에서 다음 멈춤 지점으로, 반대 방향이면 이전 멈춤 지점으로 이어서 간다. 모션을 다 보지 않아도 넘길 수 있다.
- 키보드·점 내비게이션도 같은 규칙. 동작 줄이기는 즉시 이동 유지.

## 설계 검토 (구현 전, 2026-10-17)

- **AR 도착이 앞쪽에 몰림** — 처음 안(화면당 420ms + easeOutCubic)으로 계산하면 AR 도착 1.93초 중 다크 패널 문구("머릿속 상상을 지우고")가 약 0.1초만 보인다. 감속 곡선이 앞쪽을 빠르게 지나가기 때문이다. → 도착 곡선을 easeInOutSine으로, AR만 화면당 600ms(약 2.8초, 문구 약 0.7초 노출)로 바꾼다. 한 입력에 한 섹션 원칙(#78)은 유지한다.
- **짧은 이동도 900ms면 굼뜸** — 마지막 → 푸터처럼 화면보다 짧은 이동은 거리에 맞춰 줄인다(위 규칙).
- **이동 중 입력** — 도착 중 끼어든 같은 방향 입력이 지금 목표를 다시 잡으면 넘어가지 않는다. 진행 중인 목표 번호를 기억해 그다음으로 간다.
- **숨은 구간을 0초로 건너뛸 때** — Spline 합체(스크롤 900~1678px)가 한 프레임에 끝나지만, 폰 레이어는 기록 직전(화면 이동 구간 안)에야 나타나므로 보이지 않는다.

## #84 후속: 목업 모션 속도 (2026-10-17)

화면 이동은 자연스러워졌지만 "목업 모션이 너무 빠르다"는 피드백. 도착 시간을 스크롤 길이 × 화면당 420ms로 일괄 계산해, 스크롤은 짧고 모션이 많은 섹션이 순식간에 지나갔다.

| 도착 화면     | 모션                                             | 이전   | 이후   |
| ------------- | ------------------------------------------------ | ------ | ------ |
| 기록          | 기록 12건 쌓임                                   | 2.10초 | 3.20초 |
| 리포트        | 상세 화면 스크롤 · 지표 막대 4개                 | 0.48초 | 1.65초 |
| 추천          | 카드 3장 펼침                                    | 0.42초 | 1.44초 |
| AR            | 박스 확대 → 다크 패널 문구 → AR 폰 · 스타일 전환 | 2.76초 | 4.00초 |
| 공유          | 토글 → QR 모달 → 폰 B → QR 비행 → 공유된 기록    | 0.85초 | 2.93초 |
| (추천 떠나기) | 카드 복귀 · 근거 데이터로 스크롤                 | 0.29초 | 0.79초 |

- 섹션마다 화면당 시간(`FULLPAGE.enter.msPerViewportBySection`)을 모션 양에 맞췄다. 떠나기는 화면당 650ms, 최대 0.9초(화면 이동을 1초 넘게 미루지 않음). 화면 이동 0.9초는 그대로.
- 기록 진입 회전(`TIMELINE.record.spinVh`)이 화면 이동 안에서 한 바퀴를 약 0.6초에 돌았다 → [-0.6, 0.15]에서 [-0.3, 0.3]으로 옮겨 폰이 정면으로 다 나타난 뒤 시작하고, 화면 이동 끝과 도착 시작에 걸쳐 약 1초 돈다(첫 카드 전에 끝남).
- 도착 중 입력은 계속 바로 받으므로 느려져도 조작을 빼앗기지 않는다.
- 검증: `pnpm verify`(314개). Chrome 1512×862 전체 시간 — 기록 4.15초, 리포트 2.57초, 추천 2.42초, AR 4.51초, 공유 4.51초(화면 이동은 0.8~0.9초 유지). 기록 진입 캡처에서 0.4~0.6초 정면 홈 → 0.8~1.2초 회전 → 1.5초 기울어진 기록 화면 → 2초 카드 쌓임.
